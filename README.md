# Демо: OpenSpec против чистого вайбкодинга

Сравнение двух подходов к реализации одной и той же нетривиальной фичи
в одном и том же репозитории, одним и тем же агентом, по одному и тому же промпту.

## Условия

- Агент — Claude Code, модель GLM 5.3, medium effort.
- База — ветка `master` (сервис броней: create / list / cancel).
- Промпт идентичен в обеих ветках; в `spec-ready` он подан через `/opsx:explore`.
- Критерий готовности задан в самом промпте: зелёный `make ai-check`.

### Промпт

```
(/opsx:explore) Добавь восстановление отменённой брони.

В течение RESTORE_WINDOW после отмены бронь можно восстановить.
RESTORE_WINDOW — из окружения, по умолчанию 10m.

POST /bookings/{id}/restore
  200 + восстановленная бронь в теле
  404, если брони с таким id нет
  Остальные коды ответов — по сложившимся в сервисе соглашениям.

Только этот эндпоинт: массового восстановления и восстановления серии целиком
не добавляй.
Покрой тестами, как принято в репозитории.
Готово, когда make ai-check зелёный.
```

Промпт намеренно недоспецифицирован: три статуса из пяти отданы на усмотрение
агента («по сложившимся соглашениям»), поведение на границе окна не оговорено.

### Ветки

- `vibe` — чистый вайбкодинг.
- `spec-ready` — слегка кастомизированный OpenSpec (конституция, скиллы, команды `/opsx:*`).

## Результаты

| | vibe | spec-ready |
|---|---|---|
| Время | ≈5 минут | ≈15 минут |
| `make ai-check` | зелёный | зелёный |
| Код фичи | +267 / −13, 4 файла | +381 / −18, 6 файлов |
| Тестов на restore | 5 | 10 |
| Покрытие `internal/booking` | 94.6% | 94.7% |
| Покрытие `cmd/booking` | 0% | 32% |

## Тезисы

**Обе реализации корректные.** Идиоматичный Go, только stdlib, соглашения репозитория
соблюдены, `ai-check` зелёный. Разница не в качестве кода, а в том, что зафиксировано.

**Архитектура разошлась осознанно.** `vibe` уносит отменённую бронь в отдельную map,
горячие пути не трогает. `spec-ready` делает мягкую отмену через `CancelledAt *time.Time`
и добавляет фильтр в три места чтения. Обе схемы рабочие; в `design.md` вариант с отдельной
map явно рассмотрен и отвергнут с обоснованием — то есть развилка не случайная.

**Наблюдаемый контракт разъехался ровно в двух местах** — и оба попали в
недоспецифицированную часть промпта:

1. Restore активной (или уже восстановленной) брони: `vibe` → 404, `spec-ready` → 400.
   У `vibe` «брони нет» и «бронь не отменена» слиты в один код.
2. Ровно на границе окна (`elapsed == RESTORE_WINDOW`): `vibe` → 410, `spec-ready` → 200.
   У `spec-ready` это записанное решение с отдельным тестом; у `vibe` граница не покрыта
   тестом вовсе — поведение получилось случайным.

Плюс валидация конфига: `RESTORE_WINDOW=0s` или `-5m` — `spec-ready` падает на старте,
`vibe` молча стартует с бесполезным окном (любой restore сразу 410).

**Главный эффект OpenSpec — протокол принятия решений.** Перед реализацией
зафиксировано 9 продуктовых решений (граница окна, 400 против 404, отсутствие side effects
при 409, поведение повторной отмены), каждое закрыто тестом. Даже неоговорённый случай
(повторный `DELETE` уже отменённой брони) помечен в `design.md` как допущение с
обоснованием. `vibe` принял те же решения молча и иначе — через месяц это неотличимо
от бага, потому что сверяться не с чем.

**Цена.** 636 строк артефактов на ~380 строк кода фичи и втрое больше времени.
Оправдано там, где решения переживают задачу; избыточно для одноразовых изменений.
