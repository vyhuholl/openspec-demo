## Context

Отмена сегодня — физическое удаление из `Store.rooms` (`store.go: Delete`).
Восстановление требует, чтобы отменённая бронь переживала отмену, поэтому данные
о ней остаются в хранилище. Мотивация — proposal.md, контракт — specs/bookings/spec.md.

## Goals / Non-Goals

**Goals:**

- Мягкая отмена и восстановление в существующих структурах, без новых слоёв.
- Детерминированное тестирование времени: `now` инжектится, окно задаётся явно.

**Non-Goals:**

- Чистка отменённых броней с истёкшим окном (решение пользователя №5).
- Массовое восстановление и работа с сериями.
- Персистентность: состояние по-прежнему живёт в памяти и умирает с процессом.

## Decisions

### 1. Мягкая отмена в той же структуре

`Booking` получает неэкспортируемое наружу поле `CancelledAt *time.Time`
с тегом `json:"-"`; активная бронь — `nil`. Отменённые брони остаются
в `s.rooms`, отдельной map отменённых нет.

Альтернатива — хранить отменённые в отдельной структуре — отвергнута: дублирование
поиска по id и вторая точка правды о состоянии брони.

### 2. Конфликт и выдача считаются только по активным броням

Проверка пересечения в `Create`, `ListByDate` и восстановлении пропускают брони
с `CancelledAt != nil`. Логика пересечения не меняется: `start.Before(b.End) && b.Start.Before(end)`.

### 3. Метод `Store.Restore(id)` возвращает готовую бронь

Ошибки — sentinel-значения в стиле существующих: `ErrNotFound` (переиспользуется),
`ErrNotCancelled` (бронь активна), `ErrRestoreExpired` (окно истекло),
`ErrConflict` (слот занят). Восстановление — поиск по id, проверка окна,
проверка конфликта с активными бронями той же комнаты и сброс `CancelledAt`
в nil под одним `mu.Lock()`: атомарно, без промежуточных состояний.

Граница окна (решение №6): отказ только при `now.Sub(cancelledAt) > window`,
то есть ровно на границе восстановление разрешено.

### 4. Время и окно приходят в `NewStore`

`NewStore(now func() time.Time, restoreWindow time.Duration)`. Прямых вызовов
`time.Now()` в пакете нет; тесты задают фиксированное время и управляемое окно.
Сигнатура меняется — вызовов два (`main.go`, тестовый хелпер `newServer`),
оба правятся в одной задаче.

Альтернатива — поле с дефолтом и сеттером — отвергнута: необязательное
состояние, которое можно забыть инициализировать.

### 5. `RESTORE_WINDOW` парсится в `main.go`

`time.ParseDuration`: пусто или переменной нет — `10m`; ошибка парсинга —
`log.Fatalf` до старта сервера (решение №8). Хранилище про окружение не знает.

### 6. Маппинг ошибок в статусы

`ErrNotFound` → 404, `ErrNotCancelled` → 400, `ErrRestoreExpired` → 410,
`ErrConflict` → 409 — по одному `errors.Is` в хендлере `restore`, как
в существующем `cancel`/`create`.

### 7. Поведение `DELETE` для уже отменённой брони — допущение

Не оговорено в требованиях. Принято: `DELETE` отменённой брони возвращает 404 —
повторная отмена имеет смысл только после восстановления (решение №7 описывает
именно цикл cancel → restore → cancel). Сброс окна повторным DELETE открыл бы
возможность держать бронь «полуживой» бесконечно. Спекой не покрывается
и тестами не фиксируется; при несогласии — `/opsx:update`.

## Risks / Trade-offs

- [Отменённые брони копятся в памяти без предела] → осознанное решение №5;
  для in-memory сервиса без персистентности рост ограничен временем жизни
  процесса. Чистка — отдельный change, если понадобится.
- [Новый статус 410 и мягкая отмена меняют наблюдаемое поведение cancel] →
  контракт зафиксирован в спеке; для клиента DELETE выглядит как раньше (204/404).
- [Смена сигнатуры `NewStore` — точечный break] → два вызова, правятся одной
  задачей до коммита.

## Migration Plan

Не применимо: in-memory хранилище, состояние не переживает рестарт, откат —
revert коммитов.
