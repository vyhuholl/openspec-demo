# Design

## Context

Кода сервиса нет, `go.mod` тоже нет. Мотивация и решения пользователя — в proposal.md, наблюдаемое поведение — в specs/bookings/spec.md. Ограничения: Go 1.26 (директива `go` в go.mod, локальный тулчейн 1.27), только stdlib, один конкретный тип хранилища без интерфейсов, HTTP-контракт тестируется в `internal/booking` через `httptest` по реальному стеку «хендлер → хранилище».

Факты о stdlib, на которых стоят решения (проверены запуском в scratchpad на тулчейне 1.27 с `go 1.26` в go.mod):

- `time.Parse(time.RFC3339, …)` принимает дробные секунды и `-00:00` (смещение 0); отклоняет строчные `t`/`z`, пробел вместо `T`, `+0000`, `2027-02-30`, секунду `60`. `Format(time.RFC3339)` дробь отбрасывает, `Format(time.RFC3339Nano)` сохраняет (`.250` → `.25`).
- `time.Parse(time.DateOnly, …)` отклоняет `2027-11-1`, `2027-02-30`, дату со временем, пробел в начале.
- `encoding/json` v1 сопоставляет ключи без учёта регистра (`{"ROOM":"x"}` попадает в поле `room`); `json.Decoder.Decode` молча принимает мусор после значения, `json.Unmarshal` — отклоняет; `json.Unmarshal("null", &map)` даёт nil-карту без ошибки.
- `encoding/json/v2` появился в API только в Go 1.27 (`api/go1.27.txt`) — при `go 1.26` недоступен.
- `http.ServeMux` отдаёт 404/405 с `text/plain`, а на `//bookings` и `/x/../bookings` — 307 с `text/html`.
- `strings.TrimSpace` считает пробелом NBSP и не считает zero-width space.

## Goals / Non-Goals

**Goals:**

- Инвариант «нет пересечений в комнате» обеспечивается хранилищем — единственным путём записи, под одной блокировкой.
- Каждый ответ, включая 404/405, — JSON с `Content-Type: application/json`.
- Все сценарии спеки проверяются через `NewHandler` + `httptest.NewRecorder`, без реального порта и без стабов.

**Non-Goals:**

- Производительность хранилища сверх линейного просмотра броней комнаты.
- Таймауты сервера, graceful shutdown, лимиты размера (proposal — идеи вне скоупа).

## Decisions

### Раскладка пакетов

```
go.mod                      module booking, go 1.26
cmd/booking/main.go         PORT -> http.Server{Handler: booking.NewHandler(booking.NewStore())}
internal/booking/
  booking.go                тип Booking (ID, Room, Start, End time.Time)
  store.go                  Store: sync.Mutex + map[string][]Booking; Create, ListDay; ErrInvalid, ErrConflict
  handler.go                NewHandler, разбор запросов, JSON-ответы
  store_test.go             unit-тесты хранилища, без моков
  handler_test.go           HTTP-контракт через httptest.NewRecorder
```

Маршрутизация живёт в `internal/booking` (ответ на вопрос 7): иначе 404/405 не проверить тестами пакета. `main.go` только читает `PORT` (`cmp.Or(os.Getenv("PORT"), "8080")`) и запускает сервер; ошибка `ListenAndServe` — `log.Fatal`.

### Хранилище: один мьютекс, проверка и вставка в одной критической секции

`Store` — `sync.Mutex` и `map[string][]Booking` с ключом «комната как есть». `Create(room, start, end)`:

1. проверяет доменные правила — `room` не пустая после `strings.TrimSpace`, `end.After(start)`; нарушение → `fmt.Errorf("%w: …", ErrInvalid)`;
2. под блокировкой просматривает брони комнаты: `start.Before(e.End) && e.Start.Before(end)` → `fmt.Errorf("%w: …", ErrConflict)`;
3. там же генерирует id (`crypto/rand.Text()`) и добавляет бронь.

Шаги 2 и 3 — под одним захватом, иначе два параллельных запроса оба пройдут проверку. Доменные правила в `Create`, а не только в хендлере: хранилище — единственный путь записи и само держит свои инварианты.

`ListDay(room, from, to)` под блокировкой копирует брони комнаты, пересекающиеся с `[from, to)` (`e.Start.Before(to) && from.Before(e.End)`), сортирует копию `slices.SortFunc` по `Start.Compare` и возвращает её; для пустого результата — непустой срез `make([]Booking, 0)`. Копия — чтобы сортировка и вызывающий код не трогали внутреннее состояние. Равных `start` в одной комнате не бывает (они бы пересекались), так что порядок полный.

Альтернативы: `sync.RWMutex` — выигрыш на чтениях не нужен в демо-сервисе; мьютекс на комнату или отсортированный срез с бинарным поиском — усложнение без требования.

### Время

Моменты хранятся как `time.Time`, приведённые `.UTC()`; сравнения — `Before`/`After`/`Compare`, не `==`. Разбор: `time.Parse(time.RFC3339, s)`, затем `_, off := t.Zone(); off != 0` → 400. Вывод: `t.UTC().Format(time.RFC3339Nano)` — суффикс `Z` и дробь без потерь (ответ на вопрос 2). Сутки: `from, _ := time.Parse(time.DateOnly, date)` (без зоны — UTC), `to := from.AddDate(0, 0, 1)`; в UTC перевода часов нет. От текущего времени ничего не зависит, поэтому `now func() time.Time` не вводится.

### Разбор тела POST

`io.ReadAll(r.Body)` → `json.Unmarshal(body, &map[string]json.RawMessage)` → поля `room`, `start`, `end` берутся по точному ключу; отсутствие или литерал `null` — «поле отсутствует»; каждое значение разбирается `json.Unmarshal` в `string`, ошибка типа → 400.

Почему не структура с тегами: v1 сопоставляет ключи без учёта регистра, отключить это нельзя, а `encoding/json/v2` при `go 1.26` недоступен (ответ на вопрос 4). Почему не `json.Decoder`: он принимает данные после JSON-значения, а это «тело не JSON». `null` вместо объекта даёт nil-карту и попадает в «room отсутствует» — 400 без отдельной ветки. Повторяющиеся ключи: побеждает последний — поведение `encoding/json`, контрактом не фиксируется (proposal — идеи вне скоупа).

### Разбор параметров GET

`r.URL.Query().Get("room")` и `.Get("date")`. Проверка `room` — та же функция «пустая после `strings.TrimSpace`», что и в `Create` (ответ на вопрос 5). `date` — `time.Parse(time.DateOnly, …)`.

### Маршрутизация без `http.ServeMux`

`NewHandler` возвращает `http.HandlerFunc`: путь `r.URL.Path != "/bookings"` → 404; `switch r.Method`: `POST` → создание, `GET` → выдача, иначе 405 с `Allow: GET, POST`. Для одного пути это короче связки ServeMux + резервные шаблоны и не даёт ни `text/plain`-ответов, ни 307-перенаправлений с `text/html`. HEAD получает 405 (подтверждено пользователем, см. proposal).

### Ответы

Один хелпер `writeJSON(w, status, v)`: ставит `Content-Type: application/json`, пишет статус, кодирует `v`. Ошибка кодирования после `WriteHeader` статус уже не изменит — логируется `log.Printf`. Ошибки — `{"error": "<текст>"}`. Бронь в ответе — отдельная структура с полями-строками `id`, `room`, `start`, `end` (время уже отформатировано), список — `{"bookings": […]}` без `omitempty`/`omitzero`, чтобы пустой срез сериализовался в `[]`.

Маппинг ошибок хранилища: `errors.Is(err, ErrInvalid)` → 400, `errors.Is(err, ErrConflict)` → 409, прочее → 500 с JSON-телом (недостижимо, но без паники).

### Тесты

- Пакет `booking` (внутренние тесты), стиль — table-driven, `t.Run`, `if … { t.Fatalf(…) }`, имена `TestXxx_Scenario_ExpectedResult`.
- `handler_test.go`: каждый тест собирает `s := NewStore(); h := NewHandler(s)`; хелперы `do(t, h, method, target, body)`, `mustCreate`, `listDay`, `assertErrorResponse(t, rec, status)` (статус, `Content-Type`, непустой строковый `error`). Инвариант «ни одной новой брони ни в одной комнате» проверяется тестовым хелпером, который под блокировкой считает брони во внутренней карте `s`.
- Конкурентность: 50 горутин через `wg.Go`, старт по закрытию общего канала-барьера, каждая пишет код ответа и тело в свой элемент среза; `t.Fatalf` — только после `wg.Wait()` в горутине теста. Прогон — под `-race` (`make test`).
- `store_test.go`: правило пересечения и окно суток на уровне `Store` (граница и шаг за ней), независимость возвращаемого среза от внутреннего состояния.
- Mutation-check охранных тестов (20-testing.md), наблюдаемый red записывается в tasks.md:
  - проверка и вставка под разными захватами → тесты конкурентности дают больше одного 201; удаление мьютекса → `-race` сообщает о гонке;
  - `<` → `<=` в правиле пересечения → падает тест касания; то же в окне суток → падают строки «ровно в начале/конце суток»;
  - `json.Unmarshal` → `json.Decoder.Decode` → падают «мусор после объекта» и «два JSON-значения»;
  - разбор в структуру вместо карты → падают кейсы `"ROOM"` и `"Room": "blue"`;
  - `RFC3339Nano` → `RFC3339` → падает сценарий дробных секунд;
  - удаление проверки смещения → падают кейсы `+03:00`, `-05:00`, `+00:01`;
  - nil вместо пустого среза → падает сценарий «пустой массив».

## Risks / Trade-offs

- [Один мьютекс на всё хранилище сериализует запросы к разным комнатам] → для in-memory демо приемлемо; мьютекс на комнату — если понадобится.
- [Линейный просмотр броней комнаты на каждый POST и GET] → приемлемо при ожидаемых объёмах; отсортированный срез — если понадобится.
- [Размер тела и длина `room` не ограничены — память растёт по воле клиента] → сознательно (ответ на вопрос 9), в списке идей.
- [Мутация «проверка и вставка под разными захватами» ловится тестом конкурентности вероятностно] → барьер на 50 горутин; при mutation-check прогон с `-count=20`, пока red не будет получен и записан.
- [Коллизия id из `crypto/rand.Text()`] → 128 бит случайности, вероятность пренебрежимо мала; проверка на коллизию не вводится.
- [Нет таймаутов `http.Server` — медленные клиенты держат соединения] → в списке идей; линтер по умолчанию (без gosec) этого не требует. Если `make lint` потребует — вопрос пользователю, а не молчаливое добавление.

## Migration Plan

Не применимо: новый сервис, данных и клиентов нет. Откат — удаление кода.
