# bookings Specification

## Purpose
Жизненный цикл брони переговорки: создание, отмена и восстановление отменённой
брони в пределах настраиваемого окна `RESTORE_WINDOW`, включая влияние отменённых
броней на проверку конфликтов и выдачу списка.

## Requirements

### Requirement: Восстановление отменённой брони в пределах окна
Сервис SHALL восстанавливать отменённую бронь по `POST /bookings/{id}/restore`
с кодом 200 и телом `{id, room, start, end}`, если с момента отмены прошло
не больше `RESTORE_WINDOW`. Восстановленная бронь снова участвует в конфликтах
и появляется в выдаче `GET /bookings`. Тело ответа не содержит статуса,
времени отмены и других дополнительных полей.

#### Scenario: Успешное восстановление в середине окна

```gherkin
Given RESTORE_WINDOW равен 10m
  And создана бронь в комнате "green" на 2026-08-24T10:00:00Z–2026-08-24T11:00:00Z с id, полученным в ответе
  And бронь отменена, с момента отмены прошло 5 минут
When клиент отправляет POST /bookings/{id}/restore
Then статус ответа 200
  And тело ответа содержит ту же бронь: id, room "green", start 2026-08-24T10:00:00Z, end 2026-08-24T11:00:00Z, и только эти четыре поля
  And GET /bookings?room=green&date=2026-08-24 возвращает ровно одну запись — восстановленную бронь
```

#### Scenario: Восстановление ровно на границе окна

```gherkin
Given RESTORE_WINDOW равен 10m
  And создана бронь в комнате "green" на 2026-08-24T10:00:00Z–2026-08-24T11:00:00Z с id, полученным в ответе
  And бронь отменена, с момента отмены прошло ровно 10 минут
When клиент отправляет POST /bookings/{id}/restore
Then статус ответа 200
  And тело ответа содержит восстановленную бронь с теми же id, room, start, end
```

#### Scenario: Брони с таким id нет

```gherkin
Given хранилище не содержит брони с id "deadbeef"
When клиент отправляет POST /bookings/deadbeef/restore
Then статус ответа 404
  And тело ответа содержит непустое поле error
  And в хранилище не появилось новых броней
```

### Requirement: Отказ восстановления за пределами окна
Сервис SHALL отказывать в восстановлении с кодом 410, если с момента отмены
прошло больше `RESTORE_WINDOW`. Бронь при этом остаётся отменённой и не меняется.

#### Scenario: Окно истекло на минуту

```gherkin
Given RESTORE_WINDOW равен 10m
  And создана бронь в комнате "green" на 2026-08-24T10:00:00Z–2026-08-24T11:00:00Z с id, полученным в ответе
  And бронь отменена, с момента отмены прошло 11 минут
When клиент отправляет POST /bookings/{id}/restore
Then статус ответа 410
  And тело ответа содержит непустое поле error
  And бронь остаётся отменённой: GET /bookings?room=green&date=2026-08-24 возвращает 0 записей
  And повторный POST /bookings/{id}/restore тоже возвращает 410
```

### Requirement: Восстановление не отменённой брони
Сервис SHALL отказывать в восстановлении активной (не отменённой) брони
с кодом 400 без изменения её состояния.

#### Scenario: Restore активной брони

```gherkin
Given создана бронь в комнате "green" на 2026-08-24T10:00:00Z–2026-08-24T11:00:00Z с id, полученным в ответе
  And бронь не отменялась
When клиент отправляет POST /bookings/{id}/restore
Then статус ответа 400
  And тело ответа содержит непустое поле error
  And бронь остаётся активной: GET /bookings?room=green&date=2026-08-24 возвращает ровно одну запись с тем же интервалом
```

#### Scenario: Повторный restore сразу после успешного восстановления

```gherkin
Given RESTORE_WINDOW равен 10m
  And создана бронь в комнате "green" на 2026-08-24T10:00:00Z–2026-08-24T11:00:00Z с id, полученным в ответе
  And бронь отменена и успешно восстановлена
When клиент повторно отправляет POST /bookings/{id}/restore
Then статус ответа 400
  And тело ответа содержит непустое поле error
```

### Requirement: Конфликт при восстановлении занятого слота
Сервис SHALL отказывать в восстановлении с кодом 409, если за время отмены
интервал брони в той же комнате пересёкся с другой активной бронью
(строгое пересечение интервалов). Ни одна из броней не меняется.

#### Scenario: Слот занят частично пересекающейся бронью

```gherkin
Given RESTORE_WINDOW равен 10m
  And создана бронь A в комнате "green" на 2026-08-24T10:00:00Z–2026-08-24T11:00:00Z, затем отменена
  And после отмены создана бронь B в комнате "green" на 2026-08-24T10:30:00Z–2026-08-24T11:30:00Z
  And с момента отмены брони A прошло 2 минуты
When клиент отправляет POST /bookings/{id A}/restore
Then статус ответа 409
  And тело ответа содержит непустое поле error
  And бронь B остаётся активной и неизменной: GET /bookings?room=green&date=2026-08-24 возвращает ровно одну запись — бронь B
  And бронь A остаётся отменённой: повторный POST /bookings/{id A}/restore возвращает 409
```

#### Scenario: Соседняя бронь вплотную не конфликтует

```gherkin
Given RESTORE_WINDOW равен 10m
  And создана бронь A в комнате "green" на 2026-08-24T10:00:00Z–2026-08-24T11:00:00Z, затем отменена
  And после отмены создана бронь B в комнате "green" на 2026-08-24T11:00:00Z–2026-08-24T12:00:00Z (начало совпадает с концом A)
  And с момента отмены брони A прошло 2 минуты
When клиент отправляет POST /bookings/{id A}/restore
Then статус ответа 200
  And GET /bookings?room=green&date=2026-08-24 возвращает ровно две записи: A и B
```

### Requirement: Отменённая бронь освобождает слот
Сервис SHALL разрешать создание новой брони на интервал, пересекающийся
с отменённой, с кодом 201. Конфликты вычисляются только по активным броням.

#### Scenario: Создание поверх отменённой

```gherkin
Given создана бронь A в комнате "green" на 2026-08-24T10:00:00Z–2026-08-24T11:00:00Z, затем отменена
When клиент создаёт бронь B в комнате "green" на 2026-08-24T10:00:00Z–2026-08-24T11:00:00Z (полное совпадение с A)
Then статус ответа 201
  And GET /bookings?room=green&date=2026-08-24 возвращает ровно одну запись — бронь B
```

### Requirement: Отменённые брони не видны в выдаче
`GET /bookings` SHALL возвращать только активные брони; отменённые брони
в выдаче отсутствуют.

#### Scenario: Выдача после отмены

```gherkin
Given созданы две брони в комнате "green": A на 2026-08-24T10:00:00Z–2026-08-24T11:00:00Z и B на 2026-08-24T13:00:00Z–2026-08-24T14:00:00Z
  And бронь A отменена
When клиент запрашивает GET /bookings?room=green&date=2026-08-24
Then статус ответа 200
  And в выдаче ровно одна запись — бронь B с интервалом 2026-08-24T13:00:00Z–2026-08-24T14:00:00Z
```

### Requirement: Повторная отмена открывает новое окно
После восстановления брони её повторная отмена SHALL начинать новое окно
восстановления: предыдущее время отмены не учитывается.

#### Scenario: Отмена после восстановления

```gherkin
Given RESTORE_WINDOW равен 10m
  And создана бронь в комнате "green" на 2026-08-24T10:00:00Z–2026-08-24T11:00:00Z с id, полученным в ответе
  And бронь отменена и успешно восстановлена
  And бронь отменена повторно, с момента второй отмены прошло 3 минуты (с момента первой — 13 минут)
When клиент отправляет POST /bookings/{id}/restore
Then статус ответа 200
  And тело ответа содержит восстановленную бронь с теми же id, room, start, end
```

### Requirement: Настройка RESTORE_WINDOW
Сервис SHALL читать `RESTORE_WINDOW` из окружения при старте в формате Go
duration. Отсутствующее или пустое значение — окно 10m. Невалидное значение
(не парсится как duration) — процесс завершается на старте с сообщением об ошибке,
не начиная слушать порт.

#### Scenario: Значение не задано

```gherkin
Given переменная окружения RESTORE_WINDOW не задана (или пуста)
When сервис запускается
Then сервис стартует и окно восстановления равно 10m
```

#### Scenario: Невалидное значение

```gherkin
Given переменная окружения RESTORE_WINDOW равна "abc"
When сервис запускается
Then процесс завершается на старте с сообщением об ошибке в логе
  And порт не открывается
```
