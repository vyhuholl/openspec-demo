# Workflow разработки

Инструмент — [OpenSpec](https://github.com/Fission-AI/OpenSpec) (`/opsx:*`), схема `spec-driven`.
Артефакты живут в `openspec/`: активные change — в `changes/`, после archive спека
промотируется в `openspec/specs/`.

## Пайплайн изменения

```
1. Запрос              формулировка пользователя в чате; отдельной доки фичи нет,
        │              единственный источник требований — сам запрос и уже
        ▼              заархивированные спеки в openspec/specs/
2. Вопросы             /opsx:explore — агент ОБЯЗАН выписать вопросы по всему, что
        │              допускает больше одной трактовки, и получить ответы
        ▼              (00-principles.md). Без этого гейта propose не запускается.
3. Сценарии            /opsx:propose — proposal, дельта-спека, tasks. Сценарии
        │              выводятся из ответов на вопросы и из существующих спек;
        ▼              проверка: make ai-check SPEC_LINT=1
4. Тесты + код         /opsx:apply — строго TDD (10-tdd.md): в каждой группе tasks
        │              тестовая задача первая, red наблюдается и записывается
        ▼
5. Самоаудит           в конце apply: таблица «сценарий спеки → конкретный тест»,
        │              без непокрытых сценариев; полный make ai-check
        ▼
6. Архив               /opsx:archive — спека уезжает в openspec/specs/
```

Изменение планов по ходу реализации — через `/opsx:update` (артефакты правятся
согласованно), не молчаливым отклонением кода от tasks.

## Гейт вопросов

Требования приходят устно и заведомо неполны. Поэтому на этапе 2:

- вопросы задаются до создания артефактов, списком, и ответы дожидаются;
- ответы пользователя фиксируются в `proposal.md` — они единственный след решения;
- допущение, принятое без подтверждения, помечается в артефактах как
  «не оговорено в требованиях»;
- уже заархивированная спека имеет приоритет над устным запросом: противоречие
  между ними — вопрос пользователю, а не молчаливое переписывание требования.

Догадка, закреплённая зелёным тестом, хуже отсутствия кода: она выглядит как решение.

## Формат сценария спеки

Текст правил — в `openspec/config.yaml`, `rules.specs`: оттуда их читает и CLI
(`openspec instructions specs --json`), и агент. Здесь — только то, что стоит
помнить без обращения к конфигу.

Заголовок сценария — markdown `#### Scenario: <имя>`; его валидирует openspec и по нему
же сверяет блоки `## MODIFIED Requirements` при архивации. Тело — блок ` ```gherkin `
с шагами Given / When / Then / And; Given и When обязательны.

Сценарий описывает результат исчерпывающе: конкретный статус вместо слова «ошибка»,
точное количество, границы интервалов в явном виде и — обязательно — чего произойти
не должно. Спека служит ТЗ, по которому агент пишет тесты: недосказанное он не пойдёт
уточнять на этапе apply, а закрепит догадкой в зелёном тесте (`00-principles.md`).

Форму проверяет `make spec-lint`, он же входит в `make ai-check SPEC_LINT=1`.
В обычный прогон `ai-check` не входит намеренно: код меняется чаще спек.
